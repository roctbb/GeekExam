# Агент Guard на сервере через WireGuard

Веб-сервис и адрес остаются одними: `https://guard.geekclass.ru`. Отдельного сайта для кабинета не требуется. Один экземпляр агента обслуживает один router_id; несколько экземпляров могут работать на том же сервере с отдельными ключами и частными адресами.

Роутер сам устанавливает служебное соединение WireGuard с сервером. Через него проходят RCI, RADIUS и HTTPS-подтверждение устройства. Ученический интернет использует прежний WAN; маршрут `0.0.0.0/0` в WireGuard не добавляется. Никакой пересылки интернет-трафика класса через сервер не требуется.

## Сеть и изоляция

- На сервере пример [WireGuard](../guard/deploy/wireguard.conf.example) использует `10.77.4.1/32`, на роутере — `10.77.4.2/30`. Проверить пересечения со всеми существующими маршрутами до установки.
- У роутера единственный AllowedIPs — `10.77.4.1/32`. Private key и готовые `.conf` хранятся вне Git, 0600. На WAN управления роутером нет.
- На сервере таблица 10409 применяется только к ответам **от** `10.77.4.1`. Это позволяет не менять обычные Docker-маршруты при пересечении с LAN кабинета. Для другого роутера нужны свои адреса и таблица. Пересекающиеся адреса разных кабинетов требуют отдельных интерфейсов/сетевых пространств, даже если веб-сервис общий.
- `DOCKER-USER` запрещает FORWARD в обе стороны WireGuard. UFW разрешает публично только UDP-порт туннеля, а RADIUS и HTTPS-подтверждение — только на частном интерфейсе и от заданных источников. Другие правила firewall не очищаются.
- На WireGuard-интерфейсе роутера ACL разрешает серверу RCI на TCP 80, ответы RADIUS и HTTPS, затем запрещает остальное. Исходящий ACL разрешает только обращения к Guard и RADIUS. Изоляция остальных сегментов сохраняется.

В кабинете DNS роутера возвращает для `guard.geekclass.ru` частный адрес `10.77.4.1`. За пределами кабинета DNS по-прежнему возвращает публичный адрес веб-сервиса. Nginx обслуживает обычный Guard на 443; закрытый HTTPS-порт 18766 того же имени обслуживает проверку устройства. `guard_https: true` явно разрешает частный TCP 443 до captive-входа. Публичные учебные сервисы остаются в обычном списке ресурсов.

HTTPS-подтверждение слушает только адрес WireGuard. Если Chilli сохраняет IP клиента, используется реальный TCP peer. Если выполняет SNAT, `nat_peer_ips` разрешает только заданные адреса роутера и требует точного совпадения живого TCP-сокета с NAT-таблицей. Нет совпадения — отказ. IP/MAC из JavaScript, тела запроса и forwarding headers не используются.

## Контейнер агента

[Dockerfile.agent](../guard/Dockerfile.agent) содержит Python 3.12, RADIUS-зависимости и `iproute2`. [Compose](../guard/deploy/agent.compose.yaml) запускает процесс как UID 10002 без capabilities, с read-only root filesystem и host network. Конфигурация/кеш конкретного роутера находятся в `/etc/geekguard/routers/<router_id>/`, 0700/0600. Пароль, RADIUS-secret и TLS находятся отдельно в `/etc/geekguard/secrets/<router_id>/` и монтируются read-only в `/secrets`. Родительский каталог секретов принадлежит root; файлы 0600 читаются только UID агента. Секреты не попадают в образ, Git, переменные окружения или API Guard. Пример структуры — [agent.server.example.json](../guard/agent.server.example.json).

При переносе пароль роутера доставляется администратором по SSH в отдельный файл агента на сервере. Он больше не остаётся исключительно на Mac; веб-приложение и база Guard его не получают. TLS-ключ также хранится отдельным закрытым файлом; обновление сертификата должно атомарно обновлять пару файлов, агент перечитывает её без смены boot_id.

`captive_portal.dns_router_ip` указывает фактический DNS-адрес, выданный ученикам (`192.168.2.1` в текущем кабинете). Он не заменяется адресом управления роутером в туннеле; иначе ACL блокирует DNS даже при полном доступе.

`control_tunnel` проверяет тип интерфейса WireGuard, его адрес и маршрут к роутеру при запуске, перед наблюдением и применением. При потере транспорта свежие положительные разрешения не выдаются; нативные сессии ограничены таймером роутера.

Для автозапуска используется [systemd-шаблон](../guard/deploy/geekguard-agent@.service). Вне монтируемой агенту директории создать `/etc/geekguard/deploy/<router_id>.env` (root, 0600): `GUARD_ROUTER_ID`, `GUARD_AGENT_IMAGE`, `GUARD_REVISION` и `GUARD_AGENT_COMPOSE` с абсолютным путём к Compose в Git-релизе. Через drop-in конкретного экземпляра добавить `Wants`/`After` для его `wg-quick@<interface>.service`. Затем включить `geekguard-agent@<router_id>.service`. Пароли в этот env-файл не помещаются; контейнер также имеет `restart: unless-stopped`.

## Переключение

1. Проверить handshake, ответ `/auth` роутера с сервера, адреса и маршруты. Проверить Guard на частном 443 из LAN до изменения DNS.
2. Собрать образы из Git; подготовить 0600-конфигурацию, RADIUS-secret и TLS. Проверить чтение RCI и запуск listener без обращения к `/agent/sync` — предварительный sync с новым boot_id отозвал бы действующие сессии.
3. Сохранить конфигурацию роутера, endpoint и состояние Mac. Подготовить автоматический возврат.
4. Остановить Mac-агент. Переключить адрес RADIUS на частный сервер. На сервере выполнить `prepare_agent_handover.py` и сразу запустить агент с `--resume-handover`. Файл одноразовый, действует 15 секунд и переносит только идентичности непрерывных ассоциаций, без разрешений.
5. Проверить сохранение boot_id/сетевых сессий, RADIUS Accept и ACL. Установить endpoint `https://guard.geekclass.ru:18766` через API Guard; затем изменить локальный DNS. Уже открытой странице может потребоваться обновление CSP.
6. Проверить реальный вход и привязку GeekExam с ученического устройства, полный/учебный режим и исключения. Только после успешного переключения отключить автозапуск Mac-агента. Два агента с одним ключом одновременно не запускаются.

При неудаче остановить серверный агент, вернуть адрес RADIUS и endpoint, убрать новый DNS override, выполнить свежий handover и запустить Mac. Старый рабочий SSID, пароль и учётные записи для этого не меняются.
