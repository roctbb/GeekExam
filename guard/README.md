# Geekclass Guard

Отдельный сервис для `guard.geekclass.ru`: управление учебными сетями из браузера, роли из Coding Projects, состояние роутеров и API для GeekExam. Существующее приложение GeekExam не использует базу или процесс Guard.

## Что реализовано

- **Кабинет → несколько роутеров → сегменты → устройства → сетевые сессии.** Каждый роутер принадлежит ровно одному кабинету. Устройства идентифицируются парой `(router_id, MAC)`, IP служит текущим адресом, а не постоянным идентификатором.
- Назначение преподавателей и учеников кабинетам. Преподаватель видит только назначенные кабинеты. Администратор имеет все преподавательские права и управляет кабинетами, роутерами, составом участников, серверами и исключениями устройств.
- Ручное ограничение кабинета, временные правила ученика, независимые ограничения отдельных контрольных, исключения устройств. Выключение одной контрольной не снимает другие ограничения.
- Приоритет: действующее исключение устройства → авторизованный преподаватель/администратор → индивидуальное правило ученика → режим кабинета → доступ только к серверу входа. Без действующей сетевой авторизации полный интернет не выдаётся даже при выключенном ограничении кабинета.
- Журнал изменений, защита CSRF, контроль версий при одновременном редактировании, отдельные машинные ключи роутеров, одноразовое подключение/перевыпуск ключа.
- SSO, синхронизация ролей сервером Coding Projects и API сетевого присутствия для **конкретной сетевой сессии**, которую впоследствии связывают с попыткой теста.
- Агент Python без внешних зависимостей: опрос RCI по LAN, исходящий HTTPS к Guard каждые 5 секунд, локальный компилятор правил. По умолчанию `observe`: не меняет роутер.

`Назначенный доступ` в таблице — желаемая настройка. Подтверждение применения видно отдельно для каждого роутера. Наблюдение, потеря связи и частичное применение не считаются успешным применением всего кабинета.

Оформление использует визуальные правила GeekExam: локальный Inter 400/500, Font Awesome, шапка `#303849`, общие цвета индиго, карточки, размеры элементов и светлая/тёмная темы. Стили и шрифты входят в независимую сборку Guard; внешние CDN не требуются в ограниченной сети.

## Границы первой версии

Ниже приведены ограничения первоначального IPv4 ACL адаптера. Для нового входа в Wi-Fi через Coding Projects используется отдельный [Captive Portal адаптер](../docs/wifi-authorization.md); модульные проверки и аппаратные проверки следует учитывать отдельно.

1. Доступны ручное подтверждение, [автоматическая LAN-привязка к попытке](../docs/automatic-device-binding.md) и вход через Captive Portal. Серверная интеграция Coding Projects поддерживает SSO и обновление каталога ролей. Обычный интернет-сайт не получает надёжный локальный IP браузера: адрес проверяется локальным агентом.
2. Присутствие сейчас подтверждается актуальной **Wi-Fi-ассоциацией**. DHCP-аренда не считается присутствием. Проводные устройства, включая проводной принтер, пока не попадают в этот агент; для них понадобится отдельный источник актуальной L2-идентификации. Wi-Fi-принтер можно оформить исключением уже в этой модели.
3. Экспериментальный enforcer работает только на **отдельном ученическом Bridge**, с локальным явным разрешением оператора. Управляющий хост агента должен находиться в другой подсети. Общий домашний/административный Bridge0 не подходит для автоматического включения этого режима.
4. Проверяется установка IPv4 ACL чтением RCI. Сброс ранее открытых TCP/QUIC/VPN-соединений не реализован. При внешнем IPv6-маршруте применение отклоняется. Защита от подмены MAC/IP и изоляция клиентов должны быть обеспечены сетью, а затем проверены на оборудовании.
5. При пропадании Guard работающий агент после 20 секунд перестаёт использовать сессионные разрешения; сохранённые исключения устройств действуют до своего срока. Сроки вычисляются от времени сервера и монотонного таймера. После перезапуска положительные разрешения из дискового кеша не восстанавливаются до синхронизации.
6. **Аварийная остановка агента или перезагрузка роутера пока не дают гарантии закрытого доступа.** Установленные ACL могут сохранить последние разрешения; их сохранение/возврат после reboot не гарантируются. Перед эксплуатацией нужны локальный watchdog, безопасная начальная конфигурация и проверка boot/recovery на конкретной модели.
7. Режим ACL с переключением двух собственных списков покрыт проверками компилятора/адаптера, но непрерывная работа и смена списков ещё не испытаны на Challenger. Ранее прошедшая телефонная проба проверяла отдельный временный ACL из `tools/network/platform_only_test.py`.
8. Разрешённый `195.133.49.12:443` открывает **все HTTPS-приложения на этом IP**, включая Guard и GeekExam. Сайт с возможностью проксирования или исполнения пользовательского кода должен сам ограничивать исходящий доступ. Доменные имена не изолируются таким IPv4 ACL.
9. GeekExam отображает сетевое присутствие и связывает попытку с конкретной сетевой сессией. Нельзя считать телефон ученика доказательством присутствия ноутбука с тестом.

Установленный на Challenger SSH открывает CLI KeeneticOS, а не Linux shell. Выполнение Python/Entware на самом устройстве пока не подтверждено. До этого агент запускается на постоянно включённом Linux-хосте в локальной сети. Доступ управления через WAN ему не нужен.

## Локальная демонстрация

Из корня репозитория:

```sh
rtk proxy python3 -m venv guard/.venv
rtk proxy guard/.venv/bin/pip install -r guard/requirements-dev.txt
rtk proxy npm --prefix guard/web ci
rtk proxy npm --prefix guard/web run build
rtk proxy guard/.venv/bin/python guard/scripts/demo.py
```

Открыть `http://127.0.0.1:8088`. Демо создаёт отдельную временную SQLite-базу и локальную имитацию SSO на порту 8089. Можно войти администратором, преподавателем кабинета 409 или учеником. Два кабинета, три роутера и устройства вымышлены. Агенты показывают наблюдение, а не фиктивное применение. Завершение — Ctrl+C; следующая демонстрация создаёт новую базу.

Проверки:

```sh
rtk proxy guard/.venv/bin/python -m pytest guard/tests -q
rtk proxy npm --prefix guard/web run build
```

Для разработки UI `npm --prefix guard/web run dev` проксирует `/api` и `/auth` на 8088. Для SSO используйте собранную версию на 8088: callback должен совпадать с настроенным origin.

## Развёртывание отдельного сервиса

Подготовлены `Dockerfile`, `compose.yaml`, образец TLS-vhost Nginx и unit агента. Конфигурация не устанавливается автоматически.

1. Создать `guard/.env` по `.env.example`, права 0600. Сгенерировать разные случайные секреты не короче 32 байт. `GUARD_CP_JWT_SECRET` должен совпадать с ключом действующего издателя SSO. Пароль Postgres в этом compose должен состоять из URL-безопасных символов, например результат `secrets.token_urlsafe(48)`.
2. Создать DNS `guard.geekclass.ru` на сервер с существующими сервисами, настроить TLS и обратный прокси по образцу `deploy/nginx.conf.example`. Не логировать query string callback: там краткоживущий SSO JWT.
3. В каталоге `guard` выполнить `docker compose up --build -d`. Guard слушает **только 127.0.0.1:8088** на хосте; Postgres не публикуется. Первый запуск создаёт собственную схему в отдельном volume.
4. Разрешить точный callback `https://guard.geekclass.ru/auth/callback` на стороне CP, включая параметр `state`. Если CP уже задаёт `aud`, согласовать `GUARD_CP_JWT_AUDIENCE`. Guard не принимает произвольный return URL от пользователя.
5. Подключить серверную синхронизацию учётных записей CP. Кеш роли действует 15 минут. Для работающих пользователей CP должен обновлять роли чаще этого срока, например раз в 5 минут; отзыв роли следует отправлять сразу. Если обновления нет, Guard требует новый SSO-вход и сессионные сетевые права истекают.
6. Войти администратором CP; создать кабинеты, назначить преподавателей/учеников, добавить роутеры с фактическим именем интерфейса сегмента. Получить код подключения агента.

`init-db` предназначен для **новой базы первой версии**. Он не выполняет миграции существующей схемы. Следующие изменения схемы требуют миграции и резервной копии. Ротация/очистка старых журналов и снимков политик пока также не автоматизирована. Нагрузочные и PostgreSQL-интеграционные проверки на целевом сервере ещё не проводились.

## Установка LAN-агента

На хосте Python 3.10+ под Linux/macOS разместить только каталог `guard_agent/` и локальную конфигурацию. Установки Flask/Postgres или всего GeekExam на агенте не требуется.

```sh
rtk proxy cp guard/agent.example.json /path/to/agent.json
rtk proxy chmod 600 /path/to/agent.json
# Отредактировать URL Guard, LAN-адрес роутера и реальные Bridge-интерфейсы.
rtk proxy python3 -m guard_agent enroll --config /path/to/agent.json
rtk proxy python3 -m guard_agent run --config /path/to/agent.json
```

Команды выполняются из каталога, содержащего `guard_agent/`. Код подключения и пароль вводятся скрыто. Ключ агента сохраняется в конфигурации 0600; пароль роутера на сервер Guard не передаётся. Для автозапуска укажите `password_file` с абсолютным локальным путём к файлу 0600, содержащему пароль. Ограничьте доступ отдельного пользователя ОС к конфигурации и кешу. Пример unit в `deploy/guard-agent.service.example` запускает **наблюдение**.

Один агент обслуживает один роутер. Несколько конфигураций можно запускать на одном LAN-хосте, если ему доступны все роутеры. Если сервер с Guard находится в интернете, он не заменяет LAN-агент.

Только после подготовки отдельного ученического сегмента и проверки восстановления: явно установить `experimental_ipv4_enforcement: true`, согласовать `student_interfaces` и запустить с `--enforce-experimental-ipv4`. Агент откажется заменять чужую привязку firewall или работать на подсети управляющего хоста. С облака нельзя передать произвольную CLI-команду или переключить локальный сегмент незаметно для оператора. Изменение набора сегментов требует обновления локальной конфигурации.

```sh
rtk proxy python3 -m guard_agent run --config /path/to/agent.json --enforce-experimental-ipv4
# После остановки агента: явное снятие только собственных списков Guard.
rtk proxy python3 -m guard_agent release --config /path/to/agent.json
```

На ошибке активные списки не удаляются автоматически, общая сеть и чужие ACL не перезаписываются. `release` сверяет результат чтением конфигурации. Не использовать экспериментальный режим во время настоящей контрольной до закрытия перечисленных выше аппаратных проверок.

## Что настроить на роутере один раз

- Сделать резервную копию и выделить отдельный ученический SSID/Bridge с отдельной подсетью; управляющий сегмент, сотрудники и оборудование должны быть подготовлены отдельно. Проверить маршрутизацию и изоляцию клиентов.
- Оставить RCI/web/SSH доступными только из доверенной LAN, обеспечить DHCP и DNS роутера. Не открывать управление из интернета.
- Обеспечить агенту стабильный адрес/доступ к роутеру и исходящий HTTPS к Guard. Уточнить поддержку ограниченной служебной учётной записи на установленной KeeneticOS.
- Проверить отсутствие внешнего IPv6 либо реализовать и испытать симметричный IPv6-фильтр. Сам агент IPv6 не выключает.
- Отдельно согласовать безопасное поведение при отключении хоста агента, потере питания и reboot, затем испытать его на тестовом SSID и устройстве.
- Для настоящей сетевой авторизации добавить Captive Portal/RADIUS или эквивалентный источник аутентифицированной связи «пользователь — устройство — кабинет». Обычная cookie Coding Projects эту связь не создаёт.

Если несколько точек Wi-Fi работают мостом через один общий шлюз, ограничения ставятся на **маршрутизирующем шлюзе**, а точки учитываются как AP. Самостоятельные роутеры разных кабинетов регистрируются отдельно, даже если используют одинаковые локальные адреса.

Точные запросы, примеры интеграции и формат политик описаны в [API.md](API.md).
